## Transition du rendu sectoriel

`SectorImageFluxVisualizer` reste temporairement disponible jusqu’au premier commit du socle commun.
Son dernier appel est retiré seulement pendant la phase finale d’affichage, lorsque la vue `Sectors`
reçoit directement `SectorMediaImageRepresentation`. La suppression du flux SCP synthétique, le
routage vers la vue sectorielle et la suppression de `SectorImageFluxVisualizer` forment ainsi une
seule transition compilable. Aucun nouveau consommateur ne doit utiliser ce visualiseur temporaire.

## Limites d’intégration avec les autres projets

Les algorithmes de reconnaissance, lecture, décodage, transformation et écriture des images restent
dans `src/RetroMediaLab.MediaEngine`. Les modules Amiga et Atari choisissent seulement le format temporaire
accepté par leur émulateur, conservent l’identité et le cycle de vie de ce média temporaire, puis
demandent la conversion à la composition de MediaEngine. Le module Amiga conserve ainsi le choix
d’un ADF détecté automatiquement ; le module Atari conserve le choix ATR ou ST selon la famille de
machine. Aucun algorithme de format n’est recopié dans ces modules.

La réorganisation physique décrite ici concerne uniquement `src/RetroMediaLab.MediaEngine` et les contrats
média communs explicitement placés dans `src/RetroMediaLab.Domain`. Elle ne réorganise pas les arborescences
de `src/RetroMediaLab.Emulation`, `src/RetroMediaLab.Emulation.Commodore`, `src/RetroMediaLab.Emulation.Atari`,
`src/RetroMediaLab.Infrastructure` ou `src/RetroMediaLab.App`. Ces projets reçoivent seulement les changements de
références et de points d’appel nécessaires pour consommer l’orchestration commune.

Ce passage décrit l'étape initiale de rangement. `RetroMediaLab.Domain` a depuis été supprimé et ses
contrats ont été répartis entre les projets propriétaires ; la répartition actuelle est décrite
dans [les frontières des bibliothèques de médias](media-library-boundaries.md).

L’orchestration reste une API de `RetroMediaLab.MediaEngine` et n’ajoute actuellement aucun contrat public
à `src/RetroMediaLab.Emulation`. Un nouveau contrat du SDK ne sera introduit que si une intégration future
ne peut pas utiliser cette API sans lui ; les modifications exactes du SDK devront alors être
inscrites dans la feuille de tâches avant toute modification de ce projet.

## Règles appliquées aux chemins cibles

- Les conteneurs de disquettes vont sous Formats/Floppy/<Format>; les niveaux constructeur sont supprimés lorsque le nom du format suffit.
- Les implémentations Raw propres a une machine conservent leur nom explicite dans Formats/Floppy/Raw sans créer un dossier par machine.
- Les modèles sectoriels vont dans Representations/Sectors; leurs constructeurs vont dans Reconstruction/Sectors; les décodeurs SCP et I86F restent dans Decoding.
- Les modèles de flux vont dans Representations/Flux; les transformations restent dans Conversion, Decoding, Encoding ou Reconstruction selon leur action.
- Les constantes partagées vont dans Constants; les fichiers générés sous obj ne sont jamais déplacés manuellement.

## Structure hybride cible

Les dossiers de nature placés à la racine accueillent seulement les types réellement partagés par
plusieurs formats ou plusieurs fonctions. Un type propre à un format reste avec ce format, même si
son nom contient `Constants`, `Enum`, `Exception`, `Function` ou `Interface`.

| Dossier racine | Contenu autorisé | Contenu refusé |
|---|---|---|
| `Constants` | Valeurs invariantes utilisées par plusieurs formats ou fonctions. | Constantes privées à un format ou à un algorithme. |
| `Enums` | Énumérations communes à plusieurs formats ou fonctions. | États internes propres à un Reader, Writer ou codec. |
| `Exceptions` | Erreurs communes émises par plusieurs domaines du moteur. | Erreurs dont le sens appartient à un seul format. |
| `Functions` | Fonctions sans état réellement partagées par plusieurs domaines. | Services, registres et algorithmes propres à un format. |
| `Interfaces` | Contrats internes communs, classés par fonction lorsque plusieurs contrats le justifient. | Interfaces propres à un seul format qui peuvent rester dans son dossier. |
| `Primitives` | Types binaires ou numériques élémentaires partagés, sans orchestration. | Modèles de média, services ou règles de format. |
| `Contracts` | Demandes, résultats et descripteurs échangés entre plusieurs fonctions de MediaEngine. | Modèles internes à un Reader ou à un système de fichiers. |

Les domaines fonctionnels conservent les traitements. Ils peuvent contenir des sous-dossiers par
famille uniquement lorsque plusieurs fichiers partagent cette responsabilité.

| Domaine | Responsabilité unique |
|---|---|
| `Formats` | Regrouper par support puis format les structures binaires, règles et composants propres aux fichiers images. |
| `Recognition` | Présélectionner et ordonner les Readers candidats sans lire intégralement un format à leur place. |
| `Reading` | Orchestrer la lecture demandée et retourner le document produit par le Reader spécialisé. |
| `Writing` | Sélectionner un Writer compatible et lui transmettre la représentation à produire. |
| `Acquisition` | Transformer une acquisition neutre déjà fournie en entrée exploitable par le moteur, sans accès matériel. |
| `Decoding` | Transformer un encodage conservé par la source en données interprétables. |
| `Encoding` | Produire un encodage demandé à partir de données structurées. |
| `Reconstruction` | Reconstruire une structure logique depuis des éléments décodés incomplets ou ordonnés. |
| `Conversion` | Coordonner Readers, transformations et Writers sans réimplémenter leurs algorithmes. |
| `Representations` | Porter les données Flux, Sectors, Blocks, OpticalTracks et Sequential sans dépendre du rendu. |
| `FileSystems` | Sonder et parcourir les systèmes de fichiers indépendamment du conteneur image. |
| `Exploration` | Détecter les volumes et construire les résultats destinés à l’Explorateur. |
| `Visualization` | Produire les descripteurs structurés nécessaires au rendu, sans WPF ni Skia. |
| `Composition` | Enregistrer les implémentations disponibles par fonction, sans algorithme de format. |

`Formats` applique toujours la hiérarchie support puis format. Pour les fichiers actuellement pris en
charge, la première famille est `Formats/Floppy`. Les futurs supports emploient
`Formats/HardDisk`, `Formats/Optical` et `Formats/Tape`. Les noms de constructeurs ou de machines ne
forment pas un niveau intermédiaire lorsque le format identifie déjà correctement les fichiers.

### Classement par support puis format

Le chemin normal est `Formats/<Support>/<Format>/<Fichier>`. Ainsi ATR va directement dans
`Formats/Floppy/Atr`, MSA dans `Formats/Floppy/Msa`, SCP dans `Formats/Floppy/Scp` et WOZ dans
`Formats/Floppy/Woz`. Les anciens niveaux `Atari`, `Amstrad`, `Acorn`, `Dec`, `Epson`, `Ibm`, `Msx`
et `Ucsd` ne sont pas conservés lorsqu’ils ne font que répéter la machine associée au format.

Les images sectorielles brutes partagent `Formats/Floppy/Raw`. Leur origine reste visible dans les
noms explicites tels que `IbmRawImageReader`, `MsxRawImageReader` ou `AppleRawImageReader`. Aucun
sous-dossier par constructeur ne sépare ces composants tant que leur nombre et leurs dépendances ne
justifient pas un ensemble autonome.

Un regroupement intermédiaire est admis seulement pour plusieurs fichiers réellement partagés entre
plusieurs formats voisins. Les composants Apple qui choisissent entre Raw, DiskCopy, NIB, 2IMG et
WOZ peuvent rester ensemble sous `Formats/Floppy/Apple` tant que leur routeur commun existe. Les
composants Commodore communs à D64, D71 et D81 utilisent `Formats/Floppy/CommodoreDos`. Ces dossiers
ne constituent pas un classement général par constructeur : ils hébergent un traitement commun
identifié et disparaissent si ce traitement est ensuite réparti entre les formats spécialisés.

### Création et suppression des dossiers

Un dossier vide ne fait jamais partie de la structure cible. Il est supprimé immédiatement après le
dernier déplacement de son contenu. Un dossier de catégorie contenant un seul fichier est également
supprimé et ce fichier remonte dans le dossier parent. Cette règle concerne notamment les anciens
sous-dossiers par machine sous `Conversion`, `Encoding`, `Recognition`, `Reconstruction` et
`FileSystems` lorsque le nom du fichier décrit déjà sa spécialisation.

Un dossier avec un seul fichier reste permis uniquement dans deux cas : le dossier représente le
format lui-même sous `Formats/<Support>/<Format>`, ou il constitue un point d’extension déjà défini
par la présente architecture et doit recevoir plusieurs composants lors des étapes suivantes. Les
domaines `Composition`, `Reading`, `Writing`, `Acquisition` et les cinq représentations communes sont
des points d’extension définis. Aucun autre dossier vide ou à fichier unique ne doit être conservé
pour anticiper un besoin hypothétique.

Avant chaque déplacement, les chemins cibles du groupe sont contrôlés ensemble afin de refuser deux
fichiers portant le même chemin. Après chaque groupe, le contenu réel est recompté. Les dossiers
devenus vides sont inscrits comme suppressions explicites dans la feuille de tâches, puis supprimés
dans cet ordre du niveau le plus profond vers le niveau parent.
