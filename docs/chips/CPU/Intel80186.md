Avant ce transfert : SS=6A87, SP=0759, AX=02AC, BX=001C, CX=0002, DX=0000, FLAGS=0246. L'exécution parcourt ensuite la table des vecteurs comme du code avant l'opcode invalide 67 à 008C. ### Opérande du saut et comparaison du code chargé

Le saut est un FF /5, ModR/M AF, vers le pointeur en `6A87:C322`, qui contient zéro. DS=ES=SS=6A87, SI=2566, DI=0040, BP=0C06. La RAM parasite a été capturée directement depuis son tableau hôte avant détachement, sans lecture de bus supplémentaire.

La comparaison au contenu du disque trouve une différence locale dans le code exécuté : la séquence disque `A29B0688269C0688169D06C333DBE8BAFF` devient en RAM `A29B0688269C0050FFAF06C333DBE8BAFF`. Les octets adjacents correspondent. Le saut vers zéro découle donc d'octets modifiés en RAM ; il faut identifier leur écriture avant d'accuser le décodage FF ou PUSH SP. L'instrumentation du saut a été retirée et le banc initial reconstruit.

### RETF imm16 — correction du 8 novembre, piste signalée par l'utilisateur

La section RET du manuel Intel 210911-001, page imprimée 3-143, impose au contraire de dépiler IP et CS puis d'ajouter l'immédiat à SP. Le fichier `Cpu80186.Instructions.cs` conserve maintenant cet immédiat dans `stackAdjustment` ; le transfert utilise toujours le chemin existant qui invalide la prélecture. Aucun cycle matériel ou autre opcode modifié.

Trois cas autonomes permanents dans `80186Tests.cs` vérifient CS:IP, SP et indicateurs : immédiat 0, immédiat 6, et SP=FFFC avec immédiat 8 (retour à SP=0008 après les deux mots dépilés). Le groupe `Chip80186Tests` passe intégralement en Debug : **127 réussites, 0 échec, 0 ignoré**, durée du groupe 125 ms. Cette durée est celle des tests, pas celle d'une machine émulée.

La présence d'une ancienne validation DOS ne prouve donc pas que l'instruction actuelle était correcte. ### Contradiction documentaire PUSH SP — vérification demandée par l'utilisateur

La [référence MASM 6.0 publiée par Microsoft](https://www.pcjs.org/documents/books/mspl13/masm/mref/) attribue au 80186 la valeur de SP avant décrémentation. À l'inverse, Robert R. Collins décrit explicitement le 80186/188 comme empilant SP après décrémentation dans [CPUID Algorithm Wars, novembre 1996](https://www.rcollins.org/ddj/Nov96/Nov96.html), et son algorithme de distinction des familles repose sur ce comportement. Il distingue ensuite le 80186 du 8086 par les accès mémoire à la frontière de segment.

Le [guide s80x86 de son auteur Jamie Iles](https://www.jamieiles.com/80186/development-guide.pdf), page 101, choisit également le comportement décrémenté du 80186. Il s'agit d'une comparaison d'implémentation, pas d'une mesure de notre part sur une puce réelle. Le manuel Intel 210911-001 consulté décrit décrémentation puis transfert sans traiter explicitement SP ; le manuel matériel 270788-001 de 1990, également archivé avec son extraction texte dans le même dossier, n'a pas fourni de clarification explicite de ce cas dans les passages trouvés.

Conclusion de cette vérification : la référence MASM ne suffit pas à qualifier le code actuel et ses deux tests d'erronés face à ces références contradictoires. **PUSH SP et ses tests restent inchangés** ; aucune correction matérielle non établie n'est appliquée. Les erreurs 0F précédemment rencontrées avec la 2.1 disparaissent déjà après correction CA ; ne pas ajouter POP CS ni tolérer 0F pour masquer ces anciens symptômes.

### Écart établi : suspension DMA lors d'un NMI

Le manuel matériel Intel 270788-001 (1990), section **8.8, page imprimée 8-6**, impose la suspension des DMA à la fin du transfert en cours lors de la réception d'un NMI. Le bit DHLT du statut d'interruption est positionné automatiquement ; il peut être effacé par logiciel et l'est par IRET. Les registres des canaux sont conservés. Cette fonction ne s'applique pas au mode esclave du contrôleur d'interruption. Le masque WritableStatus du code inclut déjà 8000, mais aucun chemin de TransferDma ne le consulte et aucun NMI/IRET ne le modifie : fonction manquante établie, indépendamment de l'attente MOS du diagnostic.

La section 9.2.1.2, page 9-2, précise par ailleurs que plusieurs NMI peuvent imbriquer leurs services sur cette famille : ne pas ajouter un blocage NMI jusqu'à IRET par analogie avec un autre x86. Les deux références sont dans le manuel archivé et son extraction texte déjà présents sous artifacts/.tmp-archives/chips/CPU/Intel/MCS80x86/80186/.

La suspension DHLT est maintenant appliquée sur front NMI matériel hors mode esclave, consultée avant tout nouveau DMA et effacée sur IRET ; l'écriture du statut permet aussi sa levée. Le transfert déjà en cours conserve ses deux voies octet. Groupe autonome final : **136 réussites, 0 échec, 0 ignoré, 204 ms** en Debug, dont six cas DHLT (arrêt logiciel, NMI avant DMA prêt, NMI pendant un mot, deux variantes mode esclave et INT 2 logiciel). Aucun blocage artificiel des NMI imbriqués ajouté. Le contrôle DOS intégré de cette correction est en cours ; aucune incidence ni performance présumée.
